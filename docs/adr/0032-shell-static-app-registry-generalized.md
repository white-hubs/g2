# Shell 用通用「静态应用注册表」概念承接个人中心一类伪应用，不特判具体 code

旧仓 `personManageMenus`（个人中心）不是后端 `getUserApplicationsGroups()` 驱动的真实业务应用，前端硬编码了一份菜单数据，并在匹配算法里显式特判 `code === "PERSON-MANAGE"` 才能让它走同一套应用/菜单切换与路由匹配逻辑。

迁移到 `@g2-shell/pc` 时改为通用机制：Shell 的应用/菜单匹配只区分「静态（本地声明，不查后端）」与「后端驱动」两类应用，具体哪些应用是静态的、菜单内容是什么，由配置声明（而非代码里的字面 code 判断）。个人中心是这个通用机制下的第一个实例，不是特殊逻辑；未来如果再出现同类「无需权限控制、所有用户固定可见」的入口，直接加一条配置，不用再改匹配算法代码。

**后续变更**：真实业务域迁移专项启动后，ADR-0036 把「后端驱动」这一类整体取消——所有域的菜单都改为域自持的 `menuContribution` 静态契约，后端不再驱动导航结构。本决定的「静态 vs 后端驱动」二分法已被 ADR-0036 取代：个人中心不再是"静态类的第一个实例"，而是和其他域一样，用 `menuContribution` 声明自己的菜单——它不再需要一个特殊的"静态应用注册表"概念来承接，本 ADR 记录的历史判断过程仍有效，但结论已被后续决定取代，实现时以 ADR-0036 为准。
