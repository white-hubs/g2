# Composition Profile 拆成「源 Profile + 版本注册表 + 已解析 Profile」，回滚即重新生成旧版本

> **部分修正（ADR-0055）**：版本注册表仍是「环境 + 逻辑名 → 具体地址/object key」的数据形状，但**不再作为本应用仓须提交的 git 权威**；由发布 CLI `generate` 产出（默认 `.deploy-out/`），归档形态仓外扩展。回滚＝换用指向旧 key 的生成注册表/存档并再发布已解析 Profile，或回到目标提交再 generate。下文「走 git 管控」仅描述 ADR-0043 当时的落点，以 0055 为准。

`deploy/compositions/*.yaml` 里的源 Profile 只圈选参与组装的范围与逻辑名（如 `platform[].name`），不直接写具体 entry 版本/地址；新增**版本注册表**：按「环境 + 逻辑名」记录当前应解析到的具体 remote 版本/地址。部署时，一个生成步骤读取源 Profile + 版本注册表当前状态，产出**已解析 Profile**（含具体 entry 版本/地址）作为真正的部署产物；门面运行时只消费已解析结果，不再反查注册表。

这解决了两个问题：一是同一份源 Profile 可以跨 dev/staging/prod 复用，环境差异下沉到版本注册表，不用为每个环境维护一份 Profile 副本；二是回滚变成统一操作——更换版本注册表里某个逻辑名的指向，重新生成并发布一份已解析 Profile。系统级客制覆盖（同一环境对所有租户生效）复用同一套指针替换机制，不是另一套流程。

进阶的「错误率超阈值自动回滚」本轮不做，依赖现有日志上报（ADR-0035/0039）人工响应；验证能力版本（ADR-0026）阶段不预支这块。

## Considered Options

- **门面运行时直连版本注册表 API 做实时查询**：能做到秒级生效，但把「浏览器到注册表服务」变成强依赖，且与「指针变化＝一次新发布」的可追溯性诉求冲突；否决，改为部署时解析、运行时只读已解析结果。
- **已解析 Profile 单独维护一套存档/版本历史机制**：多一层基础设施；否决——只要生成过程是「确定的 git commit + 注册表状态」的函数，历史天然可追溯，不需要专门存档。
