# 三方依赖治理关卡：新增依赖面默认禁止，基线名单外的例外先过质询

消费方（shell、domain、platform 自身以外的各消费方、standalone）不得在自己的 `package.json` 里直接声明三方库依赖，除非该库已被本仓某条 ADR 选定为技术基线、或已进入 MF shared singleton 白名单（如 vue、vue-router、pinia，见 ADR-0009/0018/0019；构建与语言链路如 vite/typescript/bun 同理）。判定一个库是否豁免，看的是「是否已有 ADR/白名单先例」，不是抽象的「算不算框架」——这条线由既有决议划定，本 ADR 不重新发明标准。

非基线的三方库必须走以下两条常规收敛路径之一，都不算「消费方直接依赖」的例外：完全封装在某个 `@g2-platform/*` 或 `@g2-shared/*` 包内部，消费方只拿自建接口（如 logger 对 OpenTelemetry 的封装，见 ADR-0040）；或经 platform 包重新暴露，消费方拿到的仍是该库本身，但只能通过 platform 包引入、不得在自己包里再声明一份依赖（如 antdv/vant，见 ADR-0012）。真正需要本 ADR 拦的，是第三种情况：某个应用/域想绕开以上两条路径，直接为一个既不在基线名单、也不打算走 platform 封装/暴露的三方库新增依赖声明——这类请求必须先经质询确认是否真的必要（有无平台既有能力已覆盖同类需求）、以及即便必要，是否应该借此机会把它提升为新的 platform 封装/暴露能力，而不是让它作为孤例留在单个应用里。这不否定三方库本身的技术价值（沿用 ADR-0040 的提醒：三方库允许存在，只是不允许消费方各自直接依赖），只是把「加一个新的直接依赖面」从改个 `package.json` 就能完成的动作，变成一个需要说明理由的决定点，防止旧仓 epp/cube-utils 那种多套基础库并存、收敛失效的覆辙重演。
